1 · Executive summary

The repo is a single DeepSeek Harness (DSH) plugin / bundle — a Cordis-style plugin with a host half (index.js), a web-client half (client.js), and a composition patch (cordis.patch.yml) that installs it. Its job: auto-populate and auto-update the list of llm-pi-ai providers' models so the Settings → Models section and the model dropdown show each provider's full advertised model list without hand-entry.

On every activation of the plugin — first boot, or a manual re-enable of the model-sync row on the Plugins page — and optionally on a repeating interval, the host half performs one sync pass:

  1. It reads the llm-pi-ai settings entry and, for each selected provider, asks the llm service to discover the provider's advertised models via llm.discoverModels('llm-pi-ai', {provider, baseURL, api}) (answered from the installed pi-ai catalog for catalog routes, or from GET {baseURL}/models for OpenAI-compatible / Anthropic routes).
  2. It diffs the advertised ids against the configured models[]: new ids are appended with an owner: 'model-sync' marker, plugin-owned ids that vanished from the listing are pruned only when prune: true, and a plugin-owned id that was deliberately deleted while still advertised is rejected (remembered in a plugin state file, never re-added).
  3. It writes back only what changed: the llm-pi-ai section (models changed), the plugin state file (rejections changed), and — for activation passes only — a lastSync outcome under the model-sync settings entry that the Plugins page's Last sync panel renders live.

Hand-entered entries are never rewritten or pruned (they carry no owner key); existing entries keep their ids, order, and capacities through every sync. The design keeps provenance on the entries themselves and moveable bookkeeping (rejections) out of user configuration entirely.

4 · End-to-end walkthrough

  1. 1 Entry activates. The bundle's patch (cordis.patch.yml) inserts a profile entry model-sync → package dsh-model-sync. Its apply(ctx, config) runs on first boot and on every manual re-enable from the Plugins page (see U1).
  2. 2 Wait for services. ctx.inject(['llm', 'settings'], …) holds the fiber until both the llm runtime and the settings service are available.
  3. 3 Register the outcome namespace. sctx.settings.register('model-sync', PROVENANCE_SCHEMA) declares the model-sync settings entry that will hold lastSync (the UI-facing outcome).
  4. 4 Schedule. An activation sync runs 1.5 s after services are ready (setTimeout, cleared on dispose). With intervalMinutes > 0, a setInterval additionally repeats the pass every N minutes. Disposal (disable/unmount) clears both timers.
  5. 5 Read configuration. syncProviders() clones the llm-pi-ai settings section (structuredClone) and validates that providers exists. A pre-0.7.0 document that still stored the rejection baseline under providers is migrated: baseline → state file, key stripped from settings.
  6. 6 Load state. loadStateFile() reads the JSON state file (default <dshHome>/storages/model-sync/state.json). A missing or corrupt file yields an empty baseline — the rejections are derived bookkeeping, so losing them only re-adds previously rejected ids once.
  7. 7 Discover advertised models. For each selected provider (all of them unless config.providers restricts; a missing baseURL skips it with a note), the plugin calls llm.discoverModels('llm-pi-ai', {provider, baseURL, api}). The llm-pi-ai host plugin answers catalog routes from the installed pi-ai catalog (zero network; includes capacities) and other routes by interrogating the endpoint (GET {baseURL}/models for OpenAI-compatible protocols, {root}/v1/models?limit=1000 for Anthropic Messages; replies bounded to 4 MiB, JSON parsed with tolerance for malformed rows). A discovery failure never fails the pass — the provider is skipped with a warning.
  8. 8 Merge. The pass diffs, per provider, the advertised ids against the section's models[] applying the add / prune / reject rules (§5) and updating the in-memory lastOwned baseline for the next run.
  9. 9 Write the section when needed. If any provider's models changed, settings.replace('llm-pi-ai', work) persists the updated document (the working copy is spread, not rebuilt, so hand-entered ids/order/capacities survive and the pi-ai schema fills defaults).
  10. 10 Write the state file when needed. Rejection-list changes are saved to the plugin state file — never to the settings document (settings are user configuration; rejections are sync bookkeeping).
  11. 11 Persist the outcome (activation only). Activation passes store lastSync = { at, providers: { P: { added, deleted } } } into the model-sync namespace and print the per-provider summary log line. Interval passes keep their notes in the log only and leave lastSync untouched.
  12. 12 Log. Every pass logs its trigger ([dsh-model-sync] activation sync: … / … interval sync: …) with per-provider outcome notes; activation passes add the summary line.

On the read side, the Settings → Models page and the model dropdown (U2) render the llm-pi-ai section — the sync's payoff — while the Last sync panel (U3) reads the model-sync outcome via remote.settings.describe() and refreshes itself on settings/document-updated (emitted on every namespace write) and connection resets, so it is live ≈1.5 s after the re-enable that triggered the pass.

5 · Sync rules — decision diagram

Three rules govern every model entry, with provenance carried by the per-entry owner marker ('model-sync' = auto-added; absent = hand-entered). The small diagram below is the exact decision logic syncProviders() applies per provider.

Rule semantics

  • Adds. Advertised ids that are not configured and not rejected are appended as { id, owner: 'model-sync', … }, with name / contextWindow / maxTokens / input copied when the listing reports them. Owner-marked entries are the only ones the plugin may later prune.
  • Prune (prune: true). Entries owned by the plugin whose id is no longer advertised are removed from models[] and reported as deleted. Hand-entered entries are never pruned — without the marker there is no evidence the plugin may remove them.
  • Rejected. A plugin-owned id that disappears from the section between two consecutive syncs while still being advertised is treated as a deliberate hand deletion: it is recorded in the plugin state file and never re-added. Rejections are the plugin's own bookkeeping, so they live in the state file — not in the settings document, which holds only user configuration plus the UI-rendered lastSync. Manually re-adding a rejected id clears its rejection. Because detection diffs consecutive syncs inside one activation, it only stays live with a positive intervalMinutes; a re-enable resets the in-memory baseline, so a single activation sync re-adds a deleted id.

The sync body is single-flight: a running guard drops re-entrant passes. The hosted objectives tests demonstrate the lifecycle corners: disposing before the 1.5 s settle timer fires suppresses the sync entirely; disposing mid-sync lets the old fiber finish writing while the new fiber runs its own pass (final state consistent); rapid toggles within the settle window yield exactly one sync from the surviving fiber; a re-enabled fiber with intervalMinutes > 0 restarts both activation and interval scheduling; a failing provider is skipped without failing the whole pass.

7 · Components & how they interact

Host half — index.js

  • apply(ctx, config) resolves config (intervalMinutes, prune, providers, stateFile), resolves the state-file path (config.stateFile → ctx.get('dshHomePath')(rel) → $DSH_HOME/~/.dsh), then registers the timetable via ctx.inject(['llm', 'settings'], …).
  • Service contracts relied upon: settings.register(ns, schema) → namespace scope with replace(); settings.get(ns) / settings.replace(ns, value); llm.discoverModels(ns, {provider, baseURL, api}); ctx.logger. (See §12 for a contract note on the settings surface.)
  • syncProviders() owns the merge, the three write targets, and the outcome summaries. It is pure bookkeeping over JSON data — no network, no LLM calls — everything external is delegated to llm.discoverModels.

Client half — client.js

  • Registers a module with window.__ModuleLoader__ and injects ['slots', 'locale', 'remote', 'remote.settings'].
  • LastSyncPanel renders the Last sync panel between the bundle's description and its component list: a header with the run time and one line per provider ("+2 models: a, b" / "-1 model: gone" / "no models added or removed"), localized en/zh.
  • createLastSyncSource() is a snapshot source over the model-sync namespace. It reads via ctx.remote.settings.describe() rather than a bound settings mirror deliberately: the mirror is unavailable on non-loopback origins (memory persistence), while describe() is served to every trusted origin. It refreshes on the same signals the mirror subscribes to (settings/document-updated, connection/reset), so the panel stays live after a toggle.
  • The slot seat uses ctx.slots.inject('plugins.bundle.config', …) keyed 'dsh-model-sync' rather than a bare registration because the seat is declared only once ui-plugin-manager's own entry realizes its 'main' registration — a bare register at apply time would throw "slot is not declared".

Composition & packaging

  • cordis.patch.yml — bundle-shipped insert patch adding the model-sync entry with defaults (intervalMinutes: 0, prune: false); hosts merge it into the profile composition.
  • package.json → dsh.bundle — tells the harness where the patch is, that the client half is a web bundle, and which client packages it depends on (ui-settings for the describe surface, locale for dictionaries).

8 · Data & persistence layout

StoreLocationHoldsWritten byRead by
`llm-pi-ai` settings entry profile settings document providers[P].models[] — entries with owner markers + capacities plugin, only when models changed Settings → Models page, model dropdown, pi-ai adapter configuration
`model-sync` settings entry profile settings document lastSync outcome (at + per-provider added/deleted) plugin, activation passes only Last sync panel (client.js)
plugin state file <dshHome>/storages/model-sync/state.json (configurable) per-provider rejected id lists (+ migrated legacy baseline) plugin, only when rejections changed plugin, every sync pass

The split is principled: the settings document is user configuration (the sync writes only merged model lists and the UI-facing outcome), while the rejection baseline is plugin bookkeeping and stays out of it. Provenance for pruning rides on the per-entry owner marker — a single source, no duplicated model list. Entries configured before this version carry no owner and are treated as hand-entered; clearing a provider's models and letting the plugin rebuild gives every entry full tracking.

10 · Testing

npm test runs both suites under node --test with fake timers (requires Node ≥ 20.4; ≥ 21.3 silences the flag warning). The fake harness mocks ctx.get / ctx.inject with a settings store, a canned discoverModels, a per-test temp dshHomePath, and timer disposers — mirroring the real loader's fiber semantics so disable/re-enable can be simulated. 17/17 tests pass.

  • index.test.js — boot activation sync discovers and writes once; re-enable runs a fresh activation sync; interval repeats with an interval trigger (and writes nothing up-to-date); activation summaries list added / pruned ids or "no models added or removed"; persisted rejections survive a re-enable; interval detection records a deliberate deletion in the state file (never settings); legacy documents migrate their baseline; prune removes owned-but-vanished ids and never hand-entered ones; empty sections log "nothing to sync" and write nothing.
  • index.edge.test.js — dispose before the settle timer suppresses the sync and re-enable runs exactly one; dispose mid-sync keeps both fibers consistent; rapid toggles yield exactly one sync from the final fiber; re-enable resets the deletion baseline (deleted id is re-added); disposal clears the interval and re-enable restarts it; one failing provider never rejects the pass while healthy providers still sync.

12 · Contract notes & compatibility observations

Verified match. Every integration point except the host-side settings API matches the current harness: the llm.discoverModels signature, namespaces-as-entry-ids, the plugins.bundle.config keyed slot, the settings/document-updated event, and the dshHomePath helper.
Host-side settings surface. The plugin's host code and its tests assume a settings contract of settings.register(ns, schema) → namespace scope with replace(), plus settings.get(ns) and settings.replace(ns, value). The current harness SettingsForms (0.1.7-rc.2) exposes describe / update / replace / mutate / configure — with no get(ns) and no register(ns, schema) scope API. The plugin therefore targets an older (or idealized) settings surface; wiring it against the current host would need that surface adapted (e.g. reading via describe() and writing via replace(ns, …)). The client half is current: it deliberately reads through remote.settings.describe() because the mirror is unavailable on non-loopback origins.
